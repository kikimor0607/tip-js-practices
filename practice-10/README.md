## Цель и результат

**Цель:** добавить в собственный Express-сервер операции записи (POST, PATCH, DELETE) с серверной валидацией и подключить к нему клиент ПР8.

**Результат:** сервер создаёт задачи (201 + `Location`), частично обновляет (200), удаляет (204). Тело проверяется на сервере независимо от формы: неверные поля дают 400 `VALIDATION_ERROR` со всеми ошибками в `details`, частичных изменений нет. Чтение из ПР9 сохранено. Клиент ПР8 без изменений исходного кода работает с этим сервером. Проходят 174/174 проверки.

## Реализация

| Модуль | Обязанности |
|---|---|
| `task-validation.js` | `validateTaskInput(value, { partial, categoryIds })`: тело — только JSON-объект; POST требует `title`, `priority`, `categoryId` и запрещает `id`, `completed`; PATCH принимает непустое подмножество четырёх полей, `id` запрещён; неизвестные поля — ошибка по каждому имени. Все ошибки собираются в один `details` (`Object.create(null)`, чтобы ключ `__proto__` не потерялся). Возвращает **новый** объект только с нормализованными полями. |
| `store.js` | `createTask` — id из счётчика `nextId` (не из длины массива), `completed: false`, возвращает копию. `updateTask` — применяет только переданные поля, сохраняет `id`, `null` при отсутствии. `deleteTask` — `false` при отсутствии; счётчик не уменьшается. |
| `write-routes.js` | POST: `jsonBody` → валидация → `createTask` → 201, `Location: /api/tasks/<id>`. PATCH: `requireTask` (сначала id и существование) → `jsonBody` → валидация с `partial: true` → `updateTask`, повторная проверка на `null` → 404. DELETE: `requireTask` → `deleteTask` → 204 без тела. |
| `json-body.js`, `errors.js`, `routes.js`, `app.js` | Предоставлены: 415 без `application/json`, 400 `INVALID_JSON` для пустого или битого тела, 413 больше 16 КиБ, Allow для 405, CORS с PATCH/DELETE и `Expose-Headers: Location`. |

**Без частичных изменений:** валидация полностью завершается до вызова хранилища. Проверено: `PATCH /api/tasks/4` с `{"title":"Новое имя","categoryId":999}` → 400, задача 4 осталась «Подготовить модель задач».

## Контракт

```text
POST /api/tasks {"title":"Проверить Location","priority":"low","categoryId":3}
→ 201 Created, Location: /api/tasks/37
  {"data":{"id":37,"title":"Проверить Location","completed":false,"priority":"low","categoryId":3}}

PATCH /api/tasks/36 {"completed":true}
→ 200 {"data":{"id":36,"title":"Вариант 4: вторая","completed":true,"priority":"medium","categoryId":1}}

DELETE /api/tasks/35 → 204 No Content; повторный GET /api/tasks/35 → 404 TASK_NOT_FOUND

POST /api/tasks {"title":"   ","priority":"high","categoryId":2}
→ 400 {"error":{"code":"VALIDATION_ERROR","message":"Данные задачи не прошли проверку.","details":{"title":"Название не должно быть пустым."}}}

POST /api/tasks {"priority":"high","categoryId":2}
→ 400 {"error":{"code":"VALIDATION_ERROR","message":"Данные задачи не прошли проверку.","details":{"title":"Название обязательно."}}}
```

**`INVALID_JSON` и `VALIDATION_ERROR`.** `INVALID_JSON` — тело нельзя разобрать как JSON или оно пустое (`-d ''` → «Пустое тело запроса.»). `VALIDATION_ERROR` — JSON разобран, но не соответствует контракту полей. POST вообще без `Content-Type: application/json` → 415 `UNSUPPORTED_MEDIA_TYPE`. После ошибок 400 сервер продолжает работать: следующий `GET /api/health` → 200.

## Интеграция клиента

Адрес API: `http://127.0.0.1:5505/api` (сервер ПР10). В Network запросы клиента идут на этот порт: `OPTIONS /api/tasks` → 204, `POST /api/tasks` → 201, затем `GET /api/tasks?priority=medium` → 200. Изменения исходного кода ПР8 не потребовались.

Поведение формы: при ошибке записи (сервер остановлен или 404) черновик сохраняется, показывается «Изменение не подтверждено: …», блокировка снимается. Ошибка повторного GET выводится отдельно от результата записи (проверено автоматическим тестом 12 в ПР8).

## Вариант

Сценарий варианта 4: создать задачу среднего приоритета, удалить, создать следующую — новый id больше удалённого. Перед началом выполнен reset.

| Действие / запрос | Ожидаемый результат | Фактический результат |
|---|---|---|
| Создание «Вариант 4: первая» из формы (`POST /api/tasks`, `{"title":"Вариант 4: первая","priority":"medium","categoryId":1}`) | 201, серверный id, карточка в выборке | 201, id **35**, карточка появилась в выборке `priority=medium` |
| Удаление id 35 (`DELETE /api/tasks/35`) | 204, затем GET | 204, затем `GET /api/tasks?priority=medium`; `GET /api/tasks/35` → 404 |
| Создание «Вариант 4: вторая» | Новый id больше удалённого | 201, id **36** (> 35): счётчик не переиспользует id |
| Неверный запрос напрямую: `POST /api/tasks` с `categoryId: 999` | 400, данные не изменены | 400 `VALIDATION_ERROR`, `details.categoryId: "Неизвестная категория."`; задач до и после — 13 |

## Контрольные вопросы и вывод

**Почему проверка на сервере обязательна при валидации формы?** Запрос можно отправить в обход формы (curl, DevTools), поэтому сервер сам проверяет типы, поля и категорию — это и показали прямые запросы выше.

**Почему id не берётся из длины массива?** После удаления длина уменьшается, и новый id совпал бы с уже выданным; счётчик `nextId` только растёт (35 → 36).

**Вывод.** Сервер ПР10 закрывает полный CRUD с единым форматом ошибок, без частичных изменений и с корректным назначением id; клиент ПР8 работает с ним без изменений кода. Подтверждено 174/174 тестами и ручным протоколом (сценарий 7 — автоматическим тестом). Ограничение — данные в памяти процесса.
