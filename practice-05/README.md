## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | A, B, C — синхронно (B печатается внутри `demonstrateAwait` до `await`). D и E — микрозадачи в порядке постановки: `.then` для D зарегистрирован раньше, чем `await null` поставил продолжение E. F — задача таймера, после всех микрозадач. |
| Фактический результат | A, B, C, D, E, F | Совпало с прогнозом. |
| Прогноз после добавления `G` (`Promise.resolve().then` после вызова `demonstrateAwait()`) | A, B, C, D, E, G, F | G ставится в очередь микрозадач третьим. |
| Фактический результат с `G` | A, B, C, D, E, G, F | Совпало. |

- Синхронный код: A, B, C.
- Микрозадачи: D (обработчик `.then`), E (продолжение после `await`), G (собственный обработчик).
- Таймер с задержкой `0` — отдельная задача: она выполняется только после завершения текущего стека и опустошения очереди микрозадач.
- Если удалить обработчик D, порядок остальных меток не изменится (A, B, C, E, G, F) — просто исчезнет одна микрозадача.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный API (не изменялся): маршруты задач и категорий, фильтры, ошибки, отладочные маршруты, CORS. |
| `src/api-client.js` | Транспорт: `buildUrl`, `createApiClient` → `requestJson` (GET, `Accept`, тайм-аут/отмена, статус, `Content-Type`, JSON) и единый `ApiError` с `kind`. Ничего не знает о задачах. |
| `src/task-api.js` | Предметный слой: маршруты `/tasks`, `/tasks/:id`, `/categories`, проверка фильтров до запроса и схемы ответа после, `loadInitialData` через `Promise.all`. |
| `src/variant.js` | Данные варианта: `variantNumber = 4`, `variantFilters = { priority: "medium" }`. |
| `src/main.js` | Консольный сценарий: загрузка, вывод таблицы и контрольная ошибка 404. |

`fetchFn` передаётся в `createApiClient`, чтобы модульные проверки подменяли сеть подготовленными `Response` и ошибками. HTTP-ошибки проверяются отдельно от сетевых: `fetch` обёрнут в свой `try`, а `Response` обрабатывается уже вне его — поэтому `ApiError` вида `http` не перехватывается и не превращается в `network`. JSON после разбора проверяется по контракту, потому что синтаксически корректное `{"data":"не массив"}` не является списком задач.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `new URL(baseUrl)`; только `http:`/`https:`, без `?` и `#`, иначе `TypeError`; хвостовые `/` у пути базы и ведущие `/` у `path` срезаются | client 01, 04 |
| Кодирование query-параметров | `url.searchParams.set(name, String(value))`; пропуск только `undefined`, `null`, `""`; `query` только читается | client 02, 03; С1 |
| Заголовок `Accept` | `headers: { Accept: "application/json" }`, `method: "GET"` | client 05 |
| Проверка `response.ok` | Сначала `!response.ok` → `ApiError("http")` с `status`, `code`, `details` из `payload.error`, если тело — JSON | client 08, 09, 16 |
| Проверка `Content-Type` | Для успешного ответа (кроме `204` → `null`) требуется `application/json`, иначе `invalid-response` | client 07, 10 |
| Разбор JSON | `await response.json()` в `try`; `SyntaxError` сохраняется в `cause` у `invalid-response` | client 11 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)`; при отказе `fetch` и сработавшем сигнале тайм-аута — `kind: "timeout"` | client 14; С3 |
| Внешняя отмена | `AbortSignal.any([signal, timeoutSignal])`; если отменён внешний сигнал — `kind: "aborted"` | client 15; С4 |

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач: `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]`, `meta.total = 12` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи: `[4, 13, 34]`, `meta.total = 3` |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | `1 — Учёба`, `2 — Проект`, `3 — Организация` |
| `loadInitialData({ completed: false, priority: "high" })` | `{ tasks: 3 шт., categories: 3 шт., meta: { total: 3, filters: {...} } }` |

Правила: фильтры — только `completed` (boolean), `priority` (`low`/`medium`/`high`), `categoryId` (положительное целое), `q` (строка ≤ 100 после `trim`); иначе `TypeError` до запроса. Задача — положительный безопасный целый `id` и `categoryId`, `title` 1–100 после `trim`, boolean `completed`, допустимый `priority`. Категория — положительный `id`, `name` 1–100. В коллекции `data` — массив без повторов `id`, `meta.total === data.length`. Нарушение схемы → `ApiError` с `kind: "invalid-response"`.

## Последовательная и параллельная загрузка

Временный эксперимент (скрипт вне репозитория): два запроса `/debug/delay?ms=150`.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 327.8 | 308.5 | 308.1 | ≈ 2 × 150 мс: второй запрос начинается только после первого |
| `Promise.all` | 155.3 | 156.1 | 154.5 | ≈ 150 мс: оба запроса начаты до ожидания, задержки перекрываются |

Ускорение получается потому, что независимые запросы ожидаются одновременно, а не потому что `Promise.all` что-то «запускает»: Promise создаются вызовами до `await`.

## Вывод

Реализован переиспользуемый клиент: `api-client.js` отвечает за HTTP и ошибки, `task-api.js` — за маршруты и схему данных. Наборы проверок: API 18/18, клиент 26/26, интеграция 13/13, собственные 6/6. Общий запрос вернул `[4, 13, 34]`, вариант 4 — `[1, 10, 19, 28]`.

Различия ошибок: ожидание Promise — это просто ещё не полученный результат, не ошибка. HTTP-ошибка (`http`) — сервер ответил статусом вне 2xx; `fetch` при этом не отклоняется, статус проверяется явно. Сетевая ошибка (`network`) — ответа нет совсем, `fetch` отклонён. Неверный ответ (`invalid-response`) — статус успешный, но тип, JSON или схема не соответствуют контракту. Тайм-аут (`timeout`) — запрос прерван своим сигналом по времени, явная отмена (`aborted`) — внешним сигналом вызывающего кода; оба передаются в сам `fetch`, поэтому сетевая операция действительно прерывается.
